Archivo      : diagramas-plantuml-ciclo2-ciclo3-simple.txt
Codificacion : UTF-8
Base normativ: UML2.5.pdf, "Diagrama de secuencia" (pag. 48-52)
Alcance      : CICLO#2 (9 casos de uso) + CICLO#3 (7 casos de uso) = 16 diagramas
Proposito    : version resumida, pensada para que el diagrama se lea bien
               cuando lo capturas y lo pegas en el documento.


--------------------------------------------------------------------------------
1. QUE SE SIMPLIFICO Y POR QUE
--------------------------------------------------------------------------------
Estos diagramas son la version CORTA. La version completa, con validaciones,
bucles, notificaciones y todos los pasos, esta en:
        diagramas-plantuml-uml2.5.txt  (CU1 a CU26)
Usa esa version si el profesor pide el detalle paso a paso. Usa esta version para
el cuerpo del documento, donde un diagrama con 8 objetos y 30 mensajes ya no se
entiende en una pagina.

Criterio de simplificacion aplicado a los 16 diagramas:

  * 3 a 5 participantes por diagrama (actor, interfaz, controlador, base de
    datos). Las clases de dominio se agrupan dentro del controlador, salvo las
    entidades indispensablemente nombradas (Reservation, Order, Inventory,
    PasarelaPago), porque ahi la entidad ES el objeto del caso de uso.
  * 4 a 8 mensajes por diagrama: solo los metodos importantes.
  * Un solo fragmento combinador por diagrama (alt u opt) y solo cuando aporta
    informacion. Se eliminaron los par, los grupos anidados y los bucles
    repetidos.
  * Se conserva la notacion UML 2.5 exigida: lifeline = objeto unico, tiempo de
    arriba hacia abajo, mensaje sincronico con flecha continua (->), respuesta
    con flecha discontinua (-->), foco de control (activate/deactivate) y
    creacion de objetos (create).
  * Los nombres de los metodos y de las rutas SIEMPRE son los reales del codigo.


--------------------------------------------------------------------------------
2. PARTICIPANTES Y ESTEREOTIPOS
--------------------------------------------------------------------------------
  <<actor>>     Persona o sistema externo.
  <<boundary>>  Pantalla o formulario (Angular / Flutter).
  <<control>>   Controlador o servicio (FastAPI).
  <<database>>  Base de datos.
  <<entity>>    Entidad de dominio, solo cuando el caso de uso gira sobre ella.

  Sufijo de instancia: "o1", "r1", "v1" identifican la instancia concreta, para
  cumplir la regla de que cada lifeline representa UNA sola instancia.


--------------------------------------------------------------------------------
3. COMO PEGAR EN DRAW.IO
--------------------------------------------------------------------------------
  1. Arrange > Insert > Advanced > PlantUML...  (Insertar > Avanzado > PlantUML)
  2. Copia UN bloque completo, desde su linea de inicio hasta la de cierre.
  3. Pegalo y acepta.
  Los nombres de los menus cambian segun idioma y version; si no aparece la
  opcion PlantUML, genera la imagen en plantuml.com y insertala con
  Insert > Image.

CICLO#2 - CU4  Gestionar usuarios y roles   (Administrador)
================================================================================
@startuml CU4_GestionarUsuariosRoles
title CU4 - Gestionar usuarios y roles
autonumber
actor "Administrador" as ADM <<actor>>
boundary "UsuariosComponent\n(Angular)" as UI <<boundary>>
control "UsersController\n/api/users" as C <<control>>
database "Base de datos" as BD <<database>>

ADM -> UI : abre la seccion Usuarios
activate UI
UI -> C : GET /api/users + /api/users/roles
activate C
C -> BD : SELECT usuarios JOIN roles
BD --> C : lista de usuarios y roles
C --> UI : 200 OK
deactivate C
UI --> ADM : muestra la tabla de usuarios
opt crear un usuario
  ADM -> UI : completa nombre, email y rol
  UI -> C : POST /api/users
  C -> BD : INSERT users
  BD --> C : ok
  C --> UI : 201 Created
end
deactivate UI
note right of C
  require_admin: si el rol no es
  Administrador responde 403.
end note
@enduml

CICLO#2 - CU13  Reservar prendas   (Cliente)
================================================================================
@startuml CU13_ReservarPrendas
title CU13 - Reservar prendas
autonumber
actor "Cliente" as CLI <<actor>>
boundary "ReservasComponent\n(Angular / Flutter)" as UI <<boundary>>
control "CommerceController\nPOST /api/reservations" as C <<control>>
entity "Reservation : r1" as R <<entity>>
database "Base de datos" as BD <<database>>

CLI -> UI : elige sucursal, prendas y horas
activate UI
UI -> C : POST /api/reservations(branch, items, expiration_hours)
activate C
create entity "Reservation : r1" as R <<entity>>
C -> R : crea(codigo RSV-..., estado PENDIENTE, vencimiento)
activate R
C -> BD : SELECT inventory (bloquea fila para reservar)
BD --> C : available por prenda
alt stock insuficiente
  C --> UI : 409 "Stock insuficiente"
else stock suficiente
  C -> BD : INSERT reservations + items + stock_movements
  BD --> C : ok
  R --> C : reserva confirmada
  C --> UI : 201 Created (codigo y vencimiento)
end
deactivate C
deactivate R
deactivate UI
note right of R
  La reserva RETIENE stock con un
  movimiento; todavia no lo descuenta.
end note
@enduml

title CU15 - Atender reserva en sucursal
autonumber
actor "Encargado de Sucursal" as ENC <<actor>>
boundary "SucursalComponent\n(Angular - panel de tienda)" as UI <<boundary>>
control "CommerceController\nPATCH /api/reservations/{id}/attend" as C <<control>>
database "Base de datos" as BD <<database>>

ENC -> UI : toma el codigo de la reserva
activate UI
UI -> C : PATCH /api/reservations/{id}/attend
activate C
C -> BD : SELECT reserva

alt no es personal autorizado
  C --> UI : 403 "Requiere personal de sucursal"
else reserva vencida o ya atendida
  C --> UI : 400 "Solo reservas pendientes vigentes"

  C -> BD : UPDATE reservas (ATENDIDA, fecha)\n+ INSERT notifications
  BD --> C : ok
  C --> UI : 200 OK
end
deactivate C
UI --> ENC : confirma la entrega al cliente
deactivate UI
note right of C
  require_staff: solo Administrador,
  Encargado de Sucursal o Cajero.
end note
@enduml

  El stock se descuenta al CONFIRMAR
  el pago, no aqui (ver CU19 y CU20).

CICLO#3 - CU19  Procesar pago electronico   (Cliente y pasarela de pago)
================================================================================
@startuml CU19_ProcesarPago
title CU19 - Procesar pago electronico
autonumber
actor "Cliente" as CLI <<actor>>
boundary "CheckoutComponent\n(Angular / Flutter)" as UI <<boundary>>
control "CommerceController\n/api/orders/{id}/pay" as C <<control>>
control "Pasarela de pago\n(SandboxPaymentGateway)" as G <<control>>
database "Base de datos" as BD <<database>>

CLI -> UI : paga el pedido pendiente
activate UI
UI -> C : POST /api/orders/{id}/pay(metodo, tarjeta)
activate C
C -> G : charge(monto, metodo, tarjeta)
activate G
G --> C : GatewayResult(approved o declined)
deactivate G
alt pago aceptado
  C -> BD : UPDATE pago COMPLETADO + descontar stock
  BD --> C : ok
  C --> UI : 200 OK (pedido pagado)
else pago rechazado
  C -> BD : UPDATE pago FALLIDO (sin descontar stock)
  BD --> C : ok
  C --> UI : 200 OK (pedido pendiente, puede reintentar)
end
deactivate C
UI --> CLI : resultado del pago
deactivate UI
note right of G
  Nunca se descuenta stock con un
  pago rechazado. Sandbox: es el
  entorno de pruebas del proyecto.
end note
@enduml
