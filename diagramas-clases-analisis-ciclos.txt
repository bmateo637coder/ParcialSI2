--------------------------------------------------------------------------------
1. QUE MUESTRA CADA DIAGRAMA
--------------------------------------------------------------------------------
Este es el punto de ANALISIS del PUDS, no el de diseno. Cada caso de uso tiene
su propio diagrama, y en cada uno aparecen las tres cosas que pidio el
enunciado:

  1) EL ACTOR   -> clases <<actor>> arriba, con la asociacion y la multiplicidad
                    hacia la entidad con la que interactua.
  2) LOS METODOS -> operaciones (+ / -) de cada clase. Son las operaciones de
                    dominio del caso de uso, y su nombre corresponde a la
                    funcion real que lo implementa en backend/app/api/.
  3) LAS TABLAS  -> cada clase lleva debajo, en una nota, el nombre fisico real
                    de su tabla, su clave primaria y sus claves foraneas.
                    Los nombres de tabla NO son inventados: salen de
                    __tablename__ en el codigo.

Notacion:
  +  publico          -  privado
  <<actor>>    persona externa
  <<entity>>   entidad de dominio persistente (tiene tabla)
  <<boundary>> interfaz (pantalla Angular/Flutter o servicio externo)
  <<dto>>      objeto de transferencia, NO se persiste (no tiene tabla)
  + = atributo    +( ) = metodo

Nota sobre el actor: se dibuja como class "Cliente" as CLI <<actor>> en vez de
actor "Cliente" as CLI. Los dos significan lo mismo en UML, pero la palabra
clave "actor" no la acepta el validador de PlantUML 1.2024.7 que se uso para
revisar estos 26 diagramas en diagramas de clases (si la acepta en diagramas de
secuencia). El estereotipo <<actor>> se ve igual en draw.io, asi que si
prefieres la palabra "actor" en el codigo basta cambiar esas lineas.

Las clases sin tabla (VestidorAR, PasarelaPago, RecomendadorIA, AsistenteIA,
ReporteVoz, DashboardReport) lo declaran explicitamente, para que no se lean
como un error de modelado.

  Tabla: users
  PK: id   UNIQUE: email
  FK: role_id -> roles.id
  Implementa: register()
  El alta siempre con el rol Cliente;
  la contrasena se guarda hasheada.
end note

  Tabla: roles
  PK: id
  Los 5 roles se siembran al arrancar
  (Administrador, Cliente, Cajero,
  Encargado de Sucursal, Proveedor).
end note
