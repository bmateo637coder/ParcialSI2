================================================================================
1. REGLAS DE LA NORMA APLICADAS Y SU EQUIVALENTE EN PLANTUML
================================================================================
Segun UML2.5.pdf, el diagrama de secuencia se construye sobre dos dimensiones y
se compone de dos elementos (objetos y mensajes). Cada regla del documento y su
traduccion en el codigo PlantUML de este archivo:

  (R1) DIMENSION HORIZONTAL  -> los OBJETOS que participan en la secuencia.
       En PlantUML: los lifelines declarados en el encabezado de cada diagrama.

  (R2) DIMENSION VERTICAL    -> la linea de tiempo; de arriba (menor tiempo)
       hacia abajo (mayor tiempo). En PlantUML: el orden de los mensajes de
       arriba hacia abajo. Nunca se invierte el orden temporal.

  (R3) UN OBJETO = UNA SOLA INSTANCIA (no varias). Por eso los objetos que se
       crean durante la interaccion se rotulan con su instancia, p.ej.
       "Order : o1", "Reservation : r1". Si un elemento es multivaluado se deja
       constancia de cual instancia esta trabajando.
       En PlantUML: `create ... as O` mas el sufijo de instancia en la etiqueta.

  (R4) OBJETOS PREEXISTENTES -> se situan en el eje horizontal (arriba).
       OBJETOS CREADOS DURANTE LA INTERACCION -> se situan en el momento de su
       creacion, mediante una llamada create.
       En PlantUML: declaracion inicial = preexistentes; `create` = creados aqui.

  (R5) FIN DE UN PUNTO DE VIDA -> aspa (X) al final de la linea de vida. Solo se
       marca cuando el objeto deja de existir realmente; los objetos persistentes
       NO se destruyen, su linea de vida se prolonga hasta el final del diagrama.
       En PlantUML: `destroy X` (usado solo para objetos transitorios reales:
       detectores de IA, DTOs de respuesta, capturas de audio, etc.).

  (R6) FOCO DE CONTROL -> rectangulo superpuesto a la linea de vida que indica
       el tiempo en que el objeto esta llevando a cabo trabajo.
       En PlantUML: `activate` / `deactivate` (siempre balanceados).

  (R7) MENSAJE -> flecha con el nombre del mensaje y sus argumentos, desde el
       emisor hacia el receptor. En PlantUML: `A -> B : mensaje(argumentos)`.

  (R8) RESPUESTA -> flecha DISCONTINUA. En PlantUML: `A --> B : respuesta`.

  (R9) CREATE y DESTROY -> representables a mitad de la interaccion.
       En PlantUML: `create` y `destroy`.


================================================================================
2. ESTEREOTIPOS USADOS (notacion UML estandar)
================================================================================
  <<actor>>     Persona o sistema externo.      -> `actor`
  <<boundary>>  Interfaz de usuario (pantalla).  -> `boundary`
  <<control>>   Controlador / servicio / caso de uso. -> `control`
  <<entity>>    Entidad del dominio de datos.    -> `entity`
  <<database>>  Almacenamiento persistente.       -> `database`

  Los nombres de los mensajes se toman del CODIGO REAL del proyecto:
  rutas HTTP de FastAPI, nombres de funciones y de servicios
  (get_current_user, require_admin, require_staff, _process_payment,
  SandboxPaymentGateway, _complete_order_sale, _deduct_order_stock,
  _movement, _release_reserved_stock, _expire_late, recommend, generate_answer).


================================================================================
3. COMO PEGAR CADA DIAGRAMA EN DRAW.IO
================================================================================
  Opcion A (recomendada):
     1. Abre draw.io (app.diagrams.net) y crea un lienzo en blanco.
     2. Menu  Arrange > Insert > Advanced > PlantUML...   (o "Insertar >
        Avanzado > PlantUML", segun idioma).
     3. Copia UN bloque completo (desde su linea de inicio hasta su linea de
        cierre) y pegalo.
     4. Acepta. El diagrama aparece renderizado en el lienzo.

  Opcion B: arrastra el bloque hasta el lienzo cuando draw.io detecta el texto.

  Opcion C: si tu version no muestra el menu PlantUML, genera la imagen en
     plantuml.com pasting el mismo bloque y luego inserala como imagen
     (Insert > Image) en el lienzo de draw.io.

  Notas:
   - Copia siempre el bloque ENTERO, desde su linea de inicio hasta la de cierre.
   - Un bloque = un diagrama. No pegues dos bloques en la misma ventana.
   - Cambia el titulo (title) si tu PUDS numera los casos de uso de otra forma.
   - Para renombrar la instancia edita la etiqueta, p.ej. "Order : o1" > "Order : o42".

CU1 - REGISTRARSE   (Usuario y Autenticacion / Actor: Cliente)
================================================================================
@startuml CU1_Registrarse
title CU1 - Registrarse
autonumber
actor "Cliente" as CLI <<actor>>
boundary "RegisterForm\n(Angular)" as FRM <<boundary>>
control "AuthController\nPOST /api/auth/register" as AC <<control>>
control "Security\nhash_password (bcrypt)" as SEC <<control>>
entity "Role : 'Cliente'\n(preexistente)" as R <<entity>>
database "Base de datos\n(SQLAlchemy)" as DB <<database>>

CLI -> FRM : llena formulario(nombre, email, password, confirmar)
activate FRM
FRM -> FRM : valida(campos requeridos, formato email, coinciden passwords)
alt datos invalidos
  FRM --> CLI : muestra errores de validacion
else datos validos
  FRM -> AC : POST /api/auth/register(email, password)
  activate AC
  AC -> SEC : hash_password(password)
  activate SEC
  SEC --> AC : hash bcrypt
  deactivate SEC
  create entity "User : u1" as U <<entity>>
  AC -> U : crea(email, hash, is_active=true, first_name, last_name)
  activate U
  U -> R : asigna role(nombre="Cliente")
  activate R
  R --> U : role_id
  deactivate R
  U --> AC : user
  deactivate U
  AC -> DB : INSERT users(role_id, is_active)
  activate DB
  DB --> AC : ok (user_id)
  deactivate DB
  AC --> FRM : 201 Created (UserResponse, RoleResponse)
  deactivate AC
  FRM --> CLI : "Registro exitoso" + navega a /auth
end
deactivate FRM
note right of R
  Role es preexistente: por regla R4
  se ubica en el eje horizontal.
end note
@enduml

CU2 - INICIAR SESION   (Usuario y Autenticacion / Cliente, Admin, Encargado, Cajero)
================================================================================
@startuml CU2_IniciarSesion
title CU2 - Iniciar sesion
autonumber
actor "Usuario" as USR <<actor>>
boundary "LoginForm\n(Angular / Flutter)" as LF <<boundary>>
control "AuthController\nPOST /api/auth/login" as AC <<control>>
control "Security\nverify_password + create_access_token" as SEC <<control>>
entity "User : u1" as U <<entity>>
entity "Role : r1" as R <<entity>>
database "Base de datos" as DB <<database>>

USR -> LF : email + password + botón Entrar
activate LF
LF -> AC : POST /api/auth/login(email, password)
activate AC
AC -> SEC : get_current_user / verificar credenciales
AC -> DB : SELECT user JOIN role WHERE email=?
activate DB
DB --> AC : user(id, hashed_password, is_active, role)
deactivate DB
AC -> R : consulta role(nombre)
activate R
R --> AC : role_name
deactivate R
alt password incorrecto o usuario inactivo
  AC -> SEC : verify_password(hash, password)
  SEC --> AC : False
  AC --> LF : 401 Unauthorized ("Credenciales inválidas")
else credenciales válidas
  AC -> SEC : verify_password(hash, password)
  SEC --> AC : True
  AC -> SEC : create_access_token(user_id, role, exp)
  SEC --> AC : token JWT
  AC --> LF : 200 OK (Token: access_token, token_type="bearer")
end
deactivate AC
LF --> USR : guarda token + navega según role_name
deactivate LF
note right of AC
  get_current_user valida el Bearer token
  en las peticiones posteriores.
end note
@enduml

CU4 - GESTIONAR USUARIOS Y ROLES   (Usuarios y roles / Administrador)
================================================================================
@startuml CU4_GestionarUsuariosRoles
title CU4 - Gestionar usuarios y roles
autonumber
actor "Administrador" as ADM <<actor>>
boundary "AdminComponent\n(sección Usuarios)" as AC <<boundary>>
control "UsersController\n/api/users" as UC <<control>>
control "Security\nrequire_admin" as SEC <<control>>
entity "User : u1" as U <<entity>>
entity "Role : r1" as R <<entity>>
database "Base de datos" as DB <<database>>

ADM -> AC : abre pestaña Usuarios
activate AC
AC -> UC : GET /api/users/roles
activate UC
UC -> SEC : require_admin(token)
activate SEC
alt rol != "Administrador"
  SEC --> UC : 403 Forbidden
  deactivate SEC
  UC --> AC : 403 ("Requiere rol de administrador")
  deactivate UC
  AC --> ADM : oculta acciones, mensaje 403
else rol == "Administrador"
  SEC --> UC : user(admin)
  deactivate SEC
  UC -> DB : SELECT roles
  DB --> UC : lista de roles
  UC --> AC : 200 OK (RoleResponse[])
  deactivate UC
  AC -> UC : GET /api/users
  activate UC
  UC -> DB : SELECT users
  DB --> UC : lista de usuarios
  UC --> AC : 200 OK (UserResponse[])
  deactivate UC
  AC --> ADM : tabla de usuarios y roles

  opt crear usuario
    ADM -> AC : llena formulario(nombre, email, role_id)
    AC -> UC : POST /api/users(datos)
    activate UC
    create entity "User : u2" as UN <<entity>>
    UC -> UN : crea(datos, is_active=true)
    activate UN
    UN -> R : asigna role(role_id)
    R --> UN : rol
    deactivate UN
    UC -> DB : INSERT users
    DB --> UC : ok
    UC --> AC : 201 Created (UserResponse)
    deactivate UC
    AC --> ADM : "Usuario creado"
  end

  opt editar o desactivar usuario
    ADM -> AC : selecciona acciones(editar / desactivar)
    AC -> UC : PATCH /api/users/{id} o DELETE /api/users/{id}
    activate UC
    UC -> U : actualiza campos / is_active=false
    activate U
    U --> UC : user
    deactivate U
    UC -> DB : UPDATE users
    DB --> UC : ok
    UC --> AC : 200 OK / 204 No Content
    deactivate UC
    AC --> ADM : "Cambios guardados"
  end
end
deactivate AC
note right of UC
  DELETE es baja logica: is_active = false
  (no se elimina la fila).
end note
@enduml

CU5 - GESTIONAR SUCURSALES   (Sucursales y Ciudades / Administrador)
================================================================================
@startuml CU5_GestionarSucursales
title CU5 - Gestionar sucursales
autonumber
actor "Administrador" as ADM <<actor>>
boundary "SucursalesComponent\n(Angular)" as BC <<boundary>>
control "BranchesController\n/api/branches" as BC2 <<control>>
control "Security\nrequire_admin" as SEC <<control>>
entity "City : c1" as CTY <<entity>>
database "Base de datos" as DB <<database>>

ADM -> BC : abre gestión de sucursales
activate BC
BC -> BC2 : GET /api/branches
activate BC2
BC2 -> DB : SELECT branches WHERE is_active=true
DB --> BC2 : lista de sucursales
BC2 --> BC : 200 OK (BranchResponse[])
deactivate BC2
BC --> ADM : tabla de sucursales

opt registrar sucursal
  ADM -> BC : nueva sucursal(nombre, ciudad, direccion, telefono)
  BC -> BC2 : POST /api/branches(datos)
  activate BC2
  BC2 -> CTY : valida ciudad(city_id)
  activate CTY
  CTY --> BC2 : ciudad válida
  deactivate CTY
  create entity "Branch : b1" as BR <<entity>>
  BC2 -> BR : crea(nombre, city_id, direccion, is_active=true)
  activate BR
  BR --> BC2 : branch
  deactivate BR
  BC2 -> DB : INSERT branches
  DB --> BC2 : ok (branch_id)
  BC2 --> BC : 201 Created (BranchResponse)
  deactivate BC2
  BC --> ADM : "Sucursal registrada"
end

opt editar sucursal
  ADM -> BC : edita datos de la sucursal
  BC -> BC2 : PATCH /api/branches/{id}(datos)
  activate BC2
  BC2 -> DB : UPDATE branches
  DB --> BC2 : ok
  BC2 --> BC : 200 OK (BranchResponse)
  deactivate BC2
  BC --> ADM : "Sucursal actualizada"
end

opt desactivar sucursal
  ADM -> BC : pulsa Desactivar
  BC -> BC2 : DELETE /api/branches/{id}
  activate BC2
  BC2 -> DB : UPDATE branches SET is_active=false
  DB --> BC2 : ok
  BC2 --> BC : 204 No Content
  deactivate BC2
  BC --> ADM : "Sucursal desactivada"
end
deactivate BC
note right of DB
  La baja es lógica: la sucursal deja de
  listarse pero conserva sus pedidos.
end note
@enduml

  PP -> PC : POST /api/providers/products(ProposalCreate)

  deactivate PR

  deactivate PC

  ADM -> PP : abre bandeja de propuestas
  PP -> PC : GET /api/providers/proposals
  activate PC
  PC -> DB : SELECT proposals WHERE estado='PENDIENTE'

  PC --> PP : 200 OK (ProposalResponse[])
  deactivate PC

    ADM -> PP : Aprueba

    activate PC
    PC -> PR : actualiza(estado="APROBADA")
    activate PR
    PR --> PC : proposal
    deactivate PR
    create entity "Product : p1" as P <<entity>>
    PC -> P : crea producto aprobado(is_active=true)
    activate P
    P --> PC : product
    deactivate P
    PC -> DB : UPDATE proposals + INSERT products
    DB --> PC : ok
    PC --> PP : 200 OK (ProposalResponse)
    deactivate PC
    PP --> ADM : "Propuesta aprobada y producto creado"
  end

  opt rechazar propuesta
    ADM -> PP : Rechaza
    PP -> PC : PATCH /api/providers/proposals/{id}/reject
    activate PC
    PC -> PR : actualiza(estado="RECHAZADA")
    activate PR
    PR --> PC : proposal
    deactivate PR
    PC -> DB : UPDATE proposals
    DB --> PC : ok
    PC --> PP : 200 OK
    deactivate PC
    PP --> ADM : "Propuesta rechazada"
  end
end

control "_complete_order_sale\n(sistema)" as SYS <<control>>

entity "OrderItem : oi1" as OI <<entity>>

entity "StockMovement : sm1" as SM <<entity>>
entity "Notification : n1" as N <<entity>>
database "Base de datos" as DB <<database>>

note over SYS
  Se dispara al CONFIRMAR un pago (CU19) o una
  venta presencial (CU18). No es una accion de
  usuario: es una reaccion del sistema.
end note

SYS -> O : _complete_order_sale(orden, usuario)
activate O
opt la orden tiene sucursal asociada
  loop por cada OrderItem de la orden
    O -> OI : lee variant_id y quantity
    activate OI
    OI --> O : order_item
    deactivate OI
    O -> INV : _deduct_order_stock -> descuenta available
    activate INV
    INV --> O : nuevo available
    deactivate INV
    O -> SM : _movement(tipo="VENTA", delta=-cantidad,\nmotivo="Venta #o1")
    activate SM
    SM --> O : stock_movement
    deactivate SM
    O -> DB : UPDATE inventory SET available=...\n+ INSERT stock_movements
    DB --> O : ok
  end
end
O -> O : status = "PAGADO"
O -> N : _notify(cliente, "Pedido pagado", total)
activate N
N --> O : notificación
deactivate N
O -> DB : INSERT notifications
DB --> O : ok
O --> SYS : venta confirmada
deactivate O
SYS --> SYS : COMMIT
@enduml

CU21 - GESTIONAR MOVIMIENTOS DE INVENTARIO   (Inventario / Encargado, Administrador)
================================================================================
@startuml CU21_GestionarMovimientos
title CU21 - Gestionar movimientos de inventario
autonumber
actor "Encargado de Sucursal" as ENC <<actor>>
boundary "InventarioComponent\n(Angular)" as IC <<boundary>>
control "InventoryController\n/api/inventory" as IC2 <<control>>
control "Security\nrequire_admin / require_staff" as SEC <<control>>
entity "Inventory : inv1" as INV <<entity>>
entity "StockMovement : sm1" as SM <<entity>>
database "Base de datos" as DB <<database>>

ENC -> IC : abre Inventario de su sucursal
activate IC
IC -> IC2 : GET /api/inventory?branch_id={b1}
activate IC2
IC2 -> SEC : require_admin / personal autorizado
activate SEC
alt rol no autorizado
  SEC --> IC2 : 403 Forbidden
  deactivate SEC
  IC2 --> IC : 403
  deactivate IC2
  IC --> ENC : "Acceso restringido"
else autorizado
  SEC --> IC2 : user(encargado)
  deactivate SEC
  IC2 -> DB : SELECT inventory WHERE branch_id=b1
  DB --> IC2 : existencias de la sucursal
  IC2 --> IC : 200 OK (InventoryResponse[])
  deactivate IC2
  IC --> ENC : tabla de existencias

  group Consultar movimientos
    ENC -> IC : pulsa "Movimientos"
    IC -> IC2 : GET /api/inventory/movements?branch_id={b1}
    activate IC2
    IC2 -> DB : SELECT stock_movements ORDER BY fecha DESC
    DB --> IC2 : lista de movimientos
    IC2 --> IC : 200 OK (StockMovementResponse[])
    deactivate IC2
    IC --> ENC : historial de entradas, salidas, ajustes y reservas
  end

  group Registrar un movimiento manual
    ENC -> IC : nueva entrada/ajuste(producto, cantidad, motivo)
    IC -> IC2 : POST /api/inventory/movements(datos)
    activate IC2
    IC2 -> INV : aplica delta al inventario
    activate INV
    alt cantidad o variante inexistente
      INV --> IC2 : error de validación
      deactivate INV
      IC2 --> IC : 404 / 400
      deactivate IC2
      IC --> ENC : "Movimiento rechazado"
    else movimiento válido
      INV --> IC2 : available actualizado
      deactivate INV
      create entity "StockMovement : sm1" as SM <<entity>>
      IC2 -> SM : crea(tipo, delta, motivo, usuario, fecha)
      activate SM
      SM --> IC2 : stock_movement
      deactivate SM
      IC2 -> DB : UPDATE inventory + INSERT stock_movements
      DB --> IC2 : ok
      IC2 --> IC : 201 Created (StockMovementResponse)
      deactivate IC2
      IC --> ENC : "Movimiento registrado"
    end
  end
end
deactivate IC
@enduml

autonumber

control "AssistantController\nPOST /api/assistant/chat" as AC <<control>>
control "assistant\ngenerate_answer(db, user, message, history)" as AS <<control>>

entity "Product : p1" as P <<entity>>
entity "Texto de la respuesta" as TX <<entity>>

activate CH

activate AC
AC -> AS : generate_answer(db, user, mensaje, historial)
activate AS
AS -> DB : SELECT conversation + historial previo
DB --> AS : historial
opt el mensaje es sobre un producto concreto
  AS -> AS : _find_products(mensaje) / _context_subject(historial)
  activate P
  P --> AS : producto de contexto
  deactivate P
  AS -> AS : _product_detail_reply / _availability_lines
else el mensaje es de stock o sucursales
  AS -> AS : _stock_reply / _branches_summary
else es sobre el último pedido
  AS -> AS : _latest_order(db, user_id)
end
create entity "Texto de la respuesta" as TX <<entity>>
AS -> TX : redacta(respuesta)
activate TX
TX --> AS : texto
deactivate TX
AS --> AC : (respuesta, productos sugeridos)
deactivate AS

alt es la primera interacción
  create entity "ChatConversation : cv1" as CV <<entity>>
  AC -> CV : crea conversación(usuario, título)
  activate CV
  CV --> AC : conversation
  deactivate CV
  AC -> DB : INSERT chat_conversations
  DB --> AC : ok
else continuación de la conversación
  AC -> CV : reutiliza conversation_id
  activate CV
  CV --> AC : conversation
  deactivate CV
end

AC -> CM : registra mensaje del cliente y respuesta
activate CM
CM --> AC : mensajes persistidos
deactivate CM
AC -> DB : INSERT chat_messages
DB --> AC : ok
AC --> CH : 200 OK (ChatResponse: respuesta + conversación)
deactivate AC
CH --> CLI : muestra la respuesta del asistente
deactivate CH
destroy TX
